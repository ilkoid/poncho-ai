## 1. Двойной счёт остатков в `warehouse_remains`

### Природа
WB в отчёте об остатках (`/api/v1/warehouse_remains`, схема `12-reports.yaml:588-692`) кладёт в массив
`warehouses[]` не только реальные склады, но и **служебные строки**, внешне неотличимые:

| Строка | Что это на самом деле |
|---|---|
| `Всего находится на складах` | **сумма всех реальных складов** — уже посчитанный итог |
| `В пути до получателей` | товар, проданный и едущий к покупателям (не на складах) |
| `В пути возвраты на склад WB` | возвраты в пути (тоже не на складах) |

Загрузчик (`flattenRemains`, `pkg/whremains/downloader.go:154`) сохраняет все строки как равноправные
склады — фильтра нет. Любой `SUM(quantity)` по товару считает весь товар **дважды**: один раз по складам,
второй раз через строку-итог (плюс добавляется «в пути», которого на складах нет).

### Доказано на данных (2026-10-11)
- В таблице **34 617 151 строка**, из них **11 965 459 (34,6%) — псевдостроки** (`LIKE 'Всего%'/'В пути%'`).
- «Всего находится на складах» — **крупнейший «склад» таблицы**: 46 824 строки в последнем снепшоте
  (больше любого реального склада).
- Эталонный пример `nm_id=13692811` (последний снепшот):

| Что суммируем | Единиц |
|---|---|
| Только реальные склады (Коледино 539, Котовск, Краснодар, Волгоград…) | **4 999** |
| Псевдостроки («Всего…» ×2 — по одному на tech_size, «В пути…») | **5 148** |
| Наивный `SUM(quantity)` | **10 147 — завышение ×2,0** |

### Как исправлять (без кода — SQL/архитектура)

**1. Перестать писать псевдостроки как склады** — в точке вставки (`flattenRemains`) фильтр:

```sql
-- писать только реальные склады:
WHERE warehouse_name NOT LIKE 'Всего%' AND warehouse_name NOT LIKE 'В пути%'
```

**2. Не выбрасывать «в пути» — это полезная метрика.** Рекомендуемая схема: добавить колонку
`row_kind TEXT` со значениями `warehouse | total | in_transit_out | in_transit_return`
(классификация теми же LIKE-правилами) и убрать псевдо-строки из «складских» выборок,
а не из таблицы.

**3. Ретро-разметка накопленных 12 млн строк** (сначала на копии, в транзакции):

```sql
ALTER TABLE warehouse_remains ADD COLUMN IF NOT EXISTS row_kind TEXT;

UPDATE warehouse_remains SET row_kind =
  CASE
    WHEN warehouse_name LIKE 'Всего%'     THEN 'total'
    WHEN warehouse_name LIKE 'В пути%'    THEN 'in_transit'
    ELSE 'warehouse'
  END
WHERE row_kind IS NULL;

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_whremains_kind
  ON warehouse_remains (snapshot_date, nm_id) WHERE row_kind = 'warehouse';
```

После разметки все существующие «итоговые» отчёты — добавить условие `row_kind = 'warehouse'`
(или `NOT LIKE`-фильтр, если разметка не внедряется).

**4. Проверка**: для любого nm_id `SUM(quantity WHERE row_kind='warehouse')` не должно превышать
значение строки `total` (±1 на округлениях) и никогда не быть кратным ей.

## 2. Схлопывание складов в `stocks_daily_warehouses` — политика WB, не баг

### Природа
С середины августа 2026 WB **скрывает географию складов** (после ударов беспилотниками) и отдаёт
остатки одним агрегатом (release-note 570, `11-analytics.yaml:5879-5890`):
`warehouseId = -999999`, `warehouseName = 'Склад WB'`, `regionName = 'Склад WB'`.
Поля `inWayToClient` / `inWayFromClient` в схеме остались; `quantity` переопределён как
«доступно клиентам для добавления в корзину».

Это сознательная политика WB — **чинить нечего, живём с агрегатом**. Загрузчик работает корректно
и молча пишет то, что отдаёт API.

### Доказано на данных

| Период | Уникальных складов в дневном снепшоте |
|---|---|
| до 15.08.2026 включительно | 113–115 реальных (Коледино, Казань, Электросталь, Новосибирск…) |
| с **16.08.2026** | ровно **1**: `-999999 / Склад WB` |

Данные свежие (последний снепшот 2026-10-09), алертов нет — ломаться нечему. Именно поэтому разрыв
незаметен: таблица «просто продолжает заполняться».

### Что делать (защита аналитики)

1. **Точка разрыва 2026-08-16**: любые ряды «динамика по складам» с датой, пересекающей 16.08.2026,
   не непрерывны. В витринах/дашбордах — либо обрезать период слева 15.08.2026, либо явно рисовать
   разделитель «география скрыта WB».
2. «Один склад» в агрегате ≠ «весь товар в одном месте»: в `-999999` сидит сумма всей сети.
3. **Гео-остатки живы в другой таблице**: `warehouse_remains` (другой эндпоинт WB) по-прежнему
   отдаёт реальные имена складов (Коледино, Электросталь, Самара…) — для географии остатков
   использовать его, а не `stocks_daily_warehouses`.
4. Периодическая сверка: `count(DISTINCT warehouse_name)` по последнему снепшоту — если вдруг
   станет >1, WB вернул географию (или начались артефакты) — сигнал посмотреть.
