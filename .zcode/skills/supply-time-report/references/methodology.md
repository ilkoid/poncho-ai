# Методология: точка отсчёта «начала доступности товаров к отгрузке»

Этот документ фиксирует, **почему** навык использует именно `updated_date` при
`status_id = 5` + фильтр `ready_for_sale_quantity > 0` как момент «начала
доступности товаров из поставки для отгрузки с конкретного склада WB», и
какие альтернативы рассмотрены и отвергнуты. Все выводы — не наугад, а из
сверки WB Swagger ↔ реальных записей в БД `wb_data_prod`.

## 1. Бизнес-задача

Вычислить среднее время от **создания поставки** до момента, когда **товары
из этой поставки становятся доступны к отгрузке с конкретного склада WB**.

- «Создание поставки» = `supplies.create_date` — однозначно, без вариантов.
- «Начало доступности к отгрузке» — неоднозначно, см. §3.

## 2. Источник данных и схема

БД `wb_data_prod`, схема `public`. Таблицы:

| Таблица | Grain | Назначение |
|---|---|---|
| `supplies` | (supply_id, preorder_id) | Заголовки поставок. Источник всех дат и количеств. |
| `supply_goods` | (supply_id, preorder_id, barcode) | Товары в поставке: barcode, nm_id, quantities. |
| `stocks_daily_warehouses` | (snapshot_date, nm_id, chrt_id, warehouse_id) | Дневные остатки по складам. Только для cross-check. |

Тип колонок дат в `supplies` — `TEXT` в формате ISO-8601
(`'2026-07-18T00:02:19+03:00'`). Приведение через
`substring(col from 1 for 10)::date`.

Swagger-спецификация WB API: `docs/wb_api_swagger/07-orders-fbw.yaml`
(`models.Supply`, `models.SupplyDetails`, `models.HandySupplyStatus`).

## 3. Кандидаты на «момент доступности»

### Вариант A — `supplies.updated_date` WHERE `status_id = 5` ✅ primary

**Что это:** дата последнего изменения записи поставки, в которой
зафиксирован переход в статус 5 (Принято).

**Почему выбрано (из сверки 239 поставок в `wb_data_prod`):**
1. `status_id = 5` присутствует у 223/239 поставок (93%); 100% совпадает со
   Swagger enum `1=NotPlanned … 5=Accepted, 6=UnloadedOnGate`.
2. `updated_date` заполнен у **100%** завершённых поставок.
3. На статусе 5 `accepted_quantity > 0` в 100% случаев (товар реально принят).
4. Quality-фильтр `ready_for_sale_quantity > 0` оставляет **196/223 (87.9%)**
   — это отсекает 27 случаев «принято, но ещё на раскладке», приближая
   метрику к «реально доступно к отгрузке».
5. Cross-check с эмпирическим появлением товаров в `stocks_daily_warehouses`
   (см. §9) — **ограниченно годный метод**. На поставках с большим числом
   уникальных nm (которых не было на складе до поставки) разница между
   `updated_date` и первой датой `quantity > 0` обычно **+1..2 дня** — то есть
   реальные товары появляются на остатках чуть позже готовности в API. Но
   для типичных поставок (где nm уже лежат от прошлых партий) cross-check
   недостоверен: по остаткам нельзя отличить «эта партия» от «старая». Поэтому
   `updated_date` — это **нижняя граница** реального срока «до размещения на
   остатках», а не точное измерение. Полный разбор ограничений cross-check —
   в §9.

   ⚠️ **Историческая правка.** В ранней версии этого документа утверждалось,
   что «`updated_date` совпадает с первой датой `quantity > 0` в стоках», с
   примером поставки 40826604 (updated_date=2026-07-17, first_stock=2026-07-17).
   При аудите выяснилось, что тот cross-check был **дефектным**: он искал
   `MIN(snapshot_date) WHERE quantity>0 AND nm_id IN (поставка)` и ловил
   **старые остатки того же nm_id** от прошлых поставок, которые лежат на
   складе месяцами. Например, nm 13279387 из поставки 40826604 уже лежал на
   Электростали 2026-07-10 (за 4 дня до создания поставки!) — но старый
   cross-check считал его «появлением из текущей поставки». Это давало ложное
   покрытие 60–100% и отрицательные лаги. Текущая версия cross-check (§9)
   использует медиану `first_seen` по всем nm поставки и честно маркируется
   как приближение.

### Вариант B — `supplies.fact_date` ❌ отвергнут

**Что это:** «Дата фактической отгрузки поставки» (по Swagger).

**Почему отвергнут:**
- В большинстве строк `fact_date` **равен `create_date`** (особенно для
  одиночных поставок, где все три даты — `create` = `fact` = `supply` — в
  один API-такт). То есть он не несёт информации о раскладке.
- Для крупных поставок `fact_date` **раньше** момента публикации готовности
  в API примерно на 1 день (см. пример 40826604: fact_date=07-16, updated_date
  =07-17). Между ними — этап раскладки WB, который `fact_date` не отражает.
- Это не «дата доступности», а «дата фактического прибытия на склад». Между
  ними — этап раскладки WB, который `fact_date` не отражает.

### Вариант C — `min(stocks_daily_warehouses.snapshot_date) WHERE quantity > 0` ⚠️ cross-check only

**Что это:** эмпирическая первая дата, когда товар лежит на конкретном складе
и доступен к отгрузке.

**Самый точный по семантике**, но три критических ограничения:

1. **25.7% поставок не сматчатся** из-за рассинхрона имён складов. В
   `supplies` 16 уникальных имён, в `stocks_daily_warehouses` — 113. Точное
   пересечение = **только 7**. Без словаря синонимов метод неприменим для
   ~50% самых частых складов (Краснодар/Тихорецкая, Склад Шушары и т.д.).

2. **Дневная гранулярность** (`snapshot_date`), не секундная. Подходит для
   суточной статистики, но не для часовых лагов.

3. **«Минус стоки»**: если весь объём поставки уже раскупили к первому
   snapshot, `quantity > 0` может не сработать; нужен более мягкий сигнал.

Поэтому в навыке вариант C доступен только как **опциональный cross-check**
через `--validate-stocks`, использующий `scripts/warehouse_aliases.yaml`.

## 4. Итоговая формула

```sql
delivery_time_days = DATE(substring(updated_date from 1 for 10))
                   - DATE(substring(create_date from 1 for 10))
WHERE status_id = 5
  AND ready_for_sale_quantity > 0
  AND create_date IS NOT NULL
  AND updated_date IS NOT NULL
  AND warehouse_name IS NOT NULL
```

Группировка: `GROUP BY warehouse_name` (агрегация по конкретному складу WB).

## 5. Swagger enum статусов поставки (для справки)

Из `docs/wb_api_swagger/07-orders-fbw.yaml`, `models.HandySupplyStatus`:

| status_id | enum name | Значение |
|---|---|---|
| 1 | `NotPlanned` | Не запланировано (supply_id = null) |
| 2 | `Planned` | Запланировано |
| 3 | `AllowUnload` | Отгрузка разрешена |
| 4 | `Accepting` | Идёт приёмка |
| 5 | `Accepted` | Принято ← **primary для навыка** |
| 6 | `UnloadedOnGate` | Отгружено на воротах (в БД пока не встречается) |

В БД `wb_data_prod` присутствуют статусы 1–5; 6 не наблюдался в окне
2026-04-02 … 2026-07-18.

## 6. Связь «поставка → конкретный склад WB»

В `supplies` есть 3 пары склад-полей:
- `warehouse_id` / `warehouse_name` — плановый склад поставки.
- `actual_warehouse_id` / `actual_warehouse_name` — склад, куда фактически
  привезли (в большинстве случаев совпадает с плановым).
- `transit_warehouse_id` / `transit_warehouse_name` — транзитный склад.

Сверка наполненности (239 строк):
- `warehouse_name` / `actual_warehouse_name` заполнены у **233/239 (97.5%)**.
- `warehouse_id` / `actual_warehouse_id` заполнены только у **77/239 (32%)**
  (только статусы 4–5).
- `transit_warehouse_id` — **всегда NULL**.

**Вывод:** для агрегации по складу используем `warehouse_name` — это
единственное склад-поле, доступное на всех статусах и надёжно заполненное.
`actual_warehouse_name` равен `warehouse_name` почти всегда; разница
пренебрежимо мала для среднего времени поставки.

## 7. Поля количеств (funnel поставки)

В `SupplyDetails` (Swagger) 5 уровней:

| Поле | Значение | Заполнено на status=5 |
|---|---|---|
| `quantity` | Добавлено в поставку, шт | 100% |
| `accepted_quantity` | Принято, шт | **100%** |
| `unloading_quantity` | На раскладке, шт | 45% |
| `ready_for_sale_quantity` | **Поступило в продажу, шт** | **87.9%** ← quality-фильтр |
| `depersonalized_quantity` | Обезличено, шт | редко |

Quality-фильтр `ready_for_sale_quantity > 0` отсекает 12.1% завершённых
поставок, где товар ещё на раскладке (`unloading_quantity > 0`). Это
приближает метрику к «реально доступно к отгрузке».

## 7.1. Ручные vs автоматические поставки (критично!)

`supplies.create_date` — это всегда «дата/время создания документа поставки
с уникальным ID», но **кто** его создал — критично различать. В данных WB
сосуществуют два совершенно разных потока поставок, которые нельзя смешивать:

### Поток A — ручные поставки менеджера

Признаки:
- `box_type_id > 0` (1=короб мелкий, 2=короб, 5=монопаллета, 6=суперсейф).
- `preorder_id > 0` (есть предзаказ → документ создан в ЛК менеджером).
- `virtual_type_id` = NULL или 0.
- `create_date` — точное время в рабочие часы (например `2026-07-14T10:40:22+03:00`).

Семантика: менеджер зашёл в ЛК WB, создал документ поставки с ID, заказал
короба, назначил склад отгрузки, напечатал этикетки, физически отгрузил.
`create_date` = именно тот момент «решение поставить», с которого мы считаем лаг.

### Поток B — автоматические поставки WB

Признаки:
- `box_type_id = 0` (виртуальная поставка, не требует физической отгрузки).
- `virtual_type_id` — тип авто-операции (enum из Swagger):
  - `0` = Перенос остатков
  - `1` = Обезличка
  - `4` = QR-поставка
  - `5` = **Допринято** ← самый частый, 100% наших авто-поставок
  - `6` = Скан-приёмка
- `preorder_id = 0` (нет предзаказа).
- `create_date` — ночное время, строго в окне **00:01–00:03**.

Семантика «Допринято» (`virtual_type_id=5`): WB создаёт поставку автоматически
ночью, когда покупатель возвращает товар в ПВЗ и тот автоматически
«допринимается» на ближайший склад. Менеджер к этому процессу не прикасается.
Объёмы мелкие (1–20 шт), лаг всегда ~0.

### Доказательство из данных `wb_data_prod` (196 завершённых поставок)

```
 hour_of_day |  n
-------------+-----
 00          | 120   ← все в окне 00:01–00:03
 09          |   2
 10          |   9
 ...         |  ...
 17          |  15   ← пик ручного создания в конце смены
 18          |   8
```

```
           group_           |  n  | with_preorder | box_type_2 | avg_ready | p50_ready
---------------------------+-----+---------------+------------+-----------+----------
 A_полуночные (00:01-00:03) | 120 |             0 |          0 |       2.9 |         2
 B_дневные (09-22)          |  76 |            76 |         76 |    8876.3 |      7577
```

Все 120 полуночных: `box_type_id=0` + `virtual_type_id=5` (Допринято).
Все 78 ручных (`box_type_id>0`): `preorder_id>0` + `box_type_id=2`.

### Почему мы фильтруем только ручные (`box_type_id > 0`)

1. **Бизнес-смысл.** Метрика навыка = «время от решения менеджера поставить
   до доступности товаров к отгрузке». Авто-«Допринято» — это не решение
   менеджера, а обработка возвратов WB. Их включение = смешивание двух
   разных бизнес-процессов.

2. **Шум.** Авто-поставки имеют лаг ~0 (создание и приёмка в один ночной
   такт) и медианный объём 2 шт. Их включение занижает метрику: в смешанном
   отчёте 116/196 поставок имеют lag=0, и медиана по складу = 0 даже там,
   где реальные ручные поставки идут 5–8 дней.

3. **`create_date` у авто-поставок не имеет бизнес-смысла.** Это время
   ночного джоба WB, а не «когда менеджер решил поставить».

### Реализация фильтра

- **Дефолт**: `only_manual=True` → SQL-фильтр `AND box_type_id > 0`.
- **Опция `--include-auto`**: отменяет фильтр, включает оба потока.
- Фильтр `box_type_id > 0` технически надёжнее, чем `virtual_type_id != 5`:
  он отсекает ВСЕ виртуальные поставки (`virtual_type_id` 0/1/4/5/6), а не
  только «Допринято».

## 7.2. Замороженные / закрытые склады WB

WB периодически замораживает склады: заказы и остатки замораживаются,
поставки, находящиеся в обработке, **никогда не переходят в `status_id=5`** и
остаются в статусах 4 (Идёт приёмка) или ниже.

**Пример:** склад «Электросталь» заморожен с 2026-07-18. Поставка `40871026`
(10203 шт, создана 2026-07-15) осталась в `status_id=4` с
`accepted_quantity=5800`, `unloading_quantity=5800`, `ready_for_sale_quantity=NULL`
— товар физически принят на склад, но из-за заморозки никогда не поступит в
продажу.

**Почему это НЕ ломает нашу метрику:**
- Фильтр `status_id = 5 AND ready_for_sale_quantity > 0` автоматически
  отсекает такие зависшие поставки — они не попадают в отчёт.
- Метрика строится **только на завершённых поставках**, которые реально
  дошли до продажи.

**Что важно помнить при интерпретации:**
1. Если склад заморожен, в отчёт **не попадут поставки после даты заморозки**
   (даже если они были созданы раньше, но зависли в status_id ≤ 4). Это
   корректно: они не дошли до доступности.
2. Поставки, завершённые (`status_id=5`) до даты заморозки, остаются в
   отчёте и валидны — они реально стали доступны к отгрузке.
3. Чтобы увидеть «зависшие» после заморозки поставки, используйте флаг
   `--include-in-progress` (он добавит статусы 1–4) или отдельный SQL:
   ```sql
   SELECT supply_id, status_id, create_date, updated_date,
          accepted_quantity, unloading_quantity, ready_for_sale_quantity
   FROM supplies
   WHERE warehouse_name = '<склад>'
     AND status_id IN (1, 2, 3, 4)
     AND substring(create_date from 1 for 10)::date >= '<дата_заморозки>';
   ```
4. Список замороженных складов нужно поддерживать вручную (в доках навыка
   или внешнем конфиге) — WB не отдаёт этот статус через API supplies.
   Текущий список (на 2026-07-20): **Электросталь** (заморожен с 2026-07-18).

## 8. Ограничения методологии

1. **Гранулярность — день.** Все даты в `supplies` — ISO-8601 с секундной
   точностью, но truncation до `::date` даёт дневную точность. Часовые лаги
   не измеряются.

2. **История поставок.** Самая ранняя завершённая поставка в БД:
   `create_date = 2026-05-07`. Это ограничено регламентностью запуска
   `download-wb-supplies-v2` (см. `cmd/data-downloaders/download-wb-supplies-v2/`),
   а не исходными данными WB API.

3. **Зависимость от качества скачивания.** Если downloader не запускался
   давно, `updated_date` может быть устаревшим относительно последнего
   изменения в WB. Алерт свежести: `MAX(create_date)` должен быть в пределах
   3 дней от сегодня; иначе запустите downloader.

4. **Качество `updated_date`.** Это «последний апдейт записи», а не
   «момент смены статуса 4→5» в чистом виде. В редких случаях (например,
   точечные изменения телефона поставки) `updated_date` мог бы обновиться
   после перехода в статус 5. На практике в `wb_data_prod` таких артефактов
   не выявлено, но следите за выбросами в `--drill-down`.

5. **`updated_date` ≠ «размещено на остатках» точно.** Это момент, когда WB
   зафиксировал готовность к продаже в API поставок. Между `updated_date` и
   фактическим «размещено на остатках» есть дополнительный зазор (публикация
   в API стоков, раскладка), который в данных отдельно не зафиксирован.
   Поэтому primary-метрика навыка — это **нижняя граница** реального срока
   «до физического размещения на остатках», а не точное измерение. См. §9.

## 9. Cross-check через `stocks_daily_warehouses` — ограничения

⚠️ **Этот раздел фиксирует принципиальное ограничение метода, выявленное при
аудите. Cross-check через стоки НЕ ЯВЛЯЕТСЯ надёжной эмпирической валидацией
для большинства поставок.**

### История расследования (почему метод неточен)

1. **Первая версия cross-check** искала `MIN(snapshot_date) WHERE quantity>0
   AND nm_id IN (поставка)`. При аудите выяснилось, что это **ловило старые
   остатки того же nm_id** от прошлых поставок — давало ложное покрытие
   60–100% с отрицательными лагами (сток «появлялся» за 5–9 дней до создания
   поставки, что физически невозможно).

2. **Вторая версия** фильтровала nm, у которых были остатки в течение 7 дней
   до `create_date`. Но это отбрасывало и реальные инкременты от текущей
   поставки (nm, у которого лежал 1 шт → стало 180 шт от поставки).

3. **Третья версия** (текущая) берёт медиану `first_seen` по всем nm поставки,
   без фильтра. Это робастно к шуму, но **тоже неточно**:

### Принципиальная проблема (нельзя устранить на этих данных)

На любом складе WB одновременно:
- В день приходят товары из **множества поставок** (один nm_id может быть в
  5+ активных поставках одновременно).
- Один и тот же nm_id **лежит на остатках месяцами** от прошлых поставок.
- API стоков даёт только aggregate `quantity` по `(nm_id, chrt_id,
  warehouse, day)` — **без tracking, какая единица из какой поставки**.

Поэтому по остаткам **невозможно** сказать, какая единица из какой поставки.
Любой cross-check — приближение, и для типичных поставок (где nm уже лежат)
результат систематически смещён в сторону «сток был раньше updated_date».

### Когда cross-check ещё работает (ограниченно)

Cross-check даёт осмысленные результаты **только для поставок с большим
числом уникальных nm**, которых не было на складе до поставки (новые артикулы,
новые коллекции). На проверенной выборке такие поставки дают лаг
`median_first_seen − updated_date ≈ +1..2 дня` — то есть эмпирически товары
появляются на остатках на 1–2 дня позже `updated_date`.

Примеры (из `wb_data_prod`, июль 2026):
- `40216803` Тула: updated=06-23, median_first_seen=06-24 → **+1 день**
- `40645891` Екатеринбург: updated=07-13, median=07-14 → **+1 день**
- `40648089` Невинномысск: updated=07-13, median=07-14 → **+1 день**
- `40674881` Новосемейкино: updated=07-12, median=07-14 → **+2 дня**

Для типичных повторных поставок (где nm уже лежат) лаг отрицательный и
недостоверен — артефакт старых остатков.

### Дополнительные ограничения данных стоков

1. **Короткая история.** `stocks_daily_warehouses` в БД хранит только 45 дней
   (на 2026-07-21: с 06-06 по 07-21). Поставки с `updated_date < 06-06`
   получают ложный лаг «+17 дней до первого snapshot».

2. **Дневная гранулярность.** Нельзя отличить «появилось в 09:00» от
   «появилось в 23:50».

3. **Aggregate по chrt_id.** Сток даётся по `chrt_id` (размер/цвет), а в
   поставке — по `barcode`. Соединение через `nm_id` теряет гранулярность.

### Вывод

Primary-метрика навыка (`updated_date − create_date`) — это **надёжная нижняя
граница** срока «до готовности к продаже по данным API WB». Cross-check через
стоки показывает, что реальное «до размещения на остатках» обычно ещё на
1–2 дня больше, но **только для поставок с уникальными nm**. Для большинства
поставок cross-check недостоверен из-за невозможности отличить партии по
остаткам. Флаг `--validate-stocks` оставлен как демонстрационный с честным
предупреждением в выводе.
