# Supply Time Report

Анализ среднего времени поставок Wildberries на конкретные склады WB. Источник
данных — PostgreSQL, таблицы `public.supplies` (заголовки поставок) и
`public.supply_goods` (товары в поставке), уже загруженные даунлоадером
`download-wb-supplies-v2`. Навык считает лаг **create_date → updated_date**
для завершённых поставок (`status_id = 5` + `ready_for_sale_quantity > 0`) и
агрегирует его по складам WB.

**Primary-метрика:** `delivery_time_days = DATE(updated_date) - DATE(create_date)`
WHERE `status_id = 5 AND ready_for_sale_quantity > 0 AND box_type_id > 0`.

⚠️ **Честная квалификация того, что измеряется:**
- **`create_date` = ровно момент, когда менеджер создал документ поставки в ЛК
  WB с присвоением уникального ID** (для ручных поставок с `box_type_id > 0`).
- **`updated_date` при `status_id=5` = момент, когда WB зафиксировал в API
  готовность товаров к продаже** (`ready_for_sale_quantity > 0`). Это близко
  к «товары приняты и готовы к раскладке», но **НЕ точное измерение
  физического размещения на остатках**. Между `updated_date` и фактическим
  «размещено на остатках» есть дополнительный зазор (публикация в API стоков,
  раскладка), который в данных отдельно не зафиксирован.

**Навык отвечает на вопрос «среднее время поставки от инициации менеджером
до готовности к продаже (по данным API WB)». Это нижняя граница реального
срока «до физического размещения на остатках».**

Cross-check через `stocks_daily_warehouses` (флаг `--validate-stocks`)
**в принципе неточен** для большинства поставок — потому что один и тот же
nm_id лежит на складе месяцами от множества поставок, и по остаткам нельзя
отличить «эта партия» от «старая». Полный разбор — `references/methodology.md` §9.

## Когда запускать

- «Сколько в среднем идёт поставка на склад X?» (Коледино, Электросталь,
  Подольск, Новосемейкино, Шушары, Невинномысск, Краснодар, Тула, Рязань, …)
- «Какой склад WB быстрее принимает поставки?», «топ самых медленных складов»
- «Сколько проходит от создания поставки до появления товаров в продаже?»
- «Лаг приёмки WB», «время до доступности к отгрузке»
- Drill-down: «покажи все поставки на Склад X», «какие поставки шли дольше всего»
- Cross-check: «сверь с реальным появлением товаров в остатках»
- «Когда последний раз скачивали supplies?», «насколько свежи данные по поставкам»

## Что считается

Для каждой поставки, завершённой статусом 5 (Принято):

```
delivery_time_days = DATE(updated_date) - DATE(create_date)
```

Фильтры primary-выборки:
- `status_id = 5` (Принято) — терминальный статус приёмки.
- `ready_for_sale_quantity > 0` — quality-фильтр, отсекает 12.1% случаев
  «товар принят, но ещё на раскладке» (`unloading_quantity > 0`).
- **`box_type_id > 0` (дефолт, см. ниже) — только ручные поставки менеджера**.
- `create_date`, `updated_date`, `warehouse_name` — не NULL.

### Ручные vs автоматические поставки (важно!)

`supplies.create_date` — это всегда «дата создания документа поставки с ID»,
но **кто** его создал — критично. В данных два совершенно разных потока:

| Поток | Признаки | Доля (в наших данных) | Объём | Поведение |
|---|---|---:|---:|---|
| **Ручные (менеджер)** | `box_type_id > 0` (1/2/5/6) + `preorder_id > 0` | 78/196 (40%) | 750–36 105 шт (медиана 7577) | Менеджер зашёл в ЛК, создал документ поставки с ID → заказал короба → отгрузил. `create_date` в рабочие часы (точное время типа `10:40:22`). |
| **Авто (WB)** | `box_type_id = 0` + `virtual_type_id = 5` (Допринято) | 120/196 (60%) | 1–20 шт (медиана 2) | WB создал сам ночным джобом в 00:01–00:03 (доприём возвратов из ПВЗ, обезличка, QR-приёмка). Менеджер к этому не прикасался. |

**По умолчанию навык считает только ручные поставки** (`box_type_id > 0`) —
это и есть «время от решения менеджера поставить до доступности к отгрузке».
Автоматические WB-поставки («Допринято» и т.п.) **не имеют бизнес-смысла** в
контексте этой метрики (менеджер ничего не решал; lag всегда ~0; это шум).

Флаг `--include-auto` отменяет фильтр и включает авто-поставки в отчёт —
используйте только если нужно оценить весь поток целиком.

Доказательство разделения (из данных `wb_data_prod`, 196 поставок):
- 120 авто-поставок созданы **ровно в 00:01–00:03** (66 в 00:02, 48 в 00:03, 6 в 00:01).
- Все 120 имеют `box_type_id=0` + `virtual_type_id=5`.
- Все 78 ручных имеют `preorder_id>0` + `box_type_id=2` (короба по предзаказу).

Агрегация по `warehouse_name` (конкретный склад WB). Метрики:
- **Среднее** (mean) — `statistics.fmean`.
- **Медиана P50** — `statistics.median`.
- **P25, P75, P90** — `numpy.percentile` (linear interpolation; fallback
  nearest-rank без numpy).
- **Min, Max** — экстремумы.

Полное обоснование — в `references/methodology.md`.

## Свежесть данных (важно)

Перед любым отчётом проверь актуальность:

```sql
SELECT MAX(substring(create_date from 1 for 10)::date) AS last_supply,
       CURRENT_DATE - MAX(substring(create_date from 1 for 10)::date) AS lag_days
FROM supplies
WHERE status_id = 5 AND ready_for_sale_quantity > 0;
```

- `lag_days ≤ 3` — данные свежие, можно работать.
- `lag_days > 3` — ⚠️ запустите `download-wb-supplies-v2` (см.
  `cmd/.configs/download-all/download-wb-supplies-PG.yaml`).

Сам скрипт тоже выводит этот алерт в stderr при запуске.

```bash

.venv/bin/python3 scripts/supply_time.py --since 2026-06-01 --until 2026-07-01

.venv/bin/python3 scripts/supply_time.py --drill-down "Электросталь" --format markdown

.venv/bin/python3 scripts/supply_time.py --validate-stocks

# переупорядочить по P90 (худший случай для 90% поставок)
.venv/bin/python3 scripts/supply_time.py --sort-by p90 --format markdown

# CSV для экспорта
.venv/bin/python3 scripts/supply_time.py --format csv > /tmp/supply-report.csv
```

**Флаги:**

| Флаг | Назначение |
|---|---|
| `--warehouse NAME` | Фильтр по имени склада (точное совпадение). |
| `--since YYYY-MM-DD` | Дата с (по `create_date`). |
| `--until YYYY-MM-DD` | Дата по (по `create_date`). |

> **Замечание про склады-одиночки.** В `supplies` много складов с 1–3

> и делает склад «самым быстрым», что ничего не значит. Для содержательных
> выводов фокусируйтесь на складах с `n_supplies ≥ 5`, либо используйте
> `--since/--until` чтобы сузить выборку до значимых.

## Workflow

1. **Резолв DSN** — из `.env` (через `scripts/db.py`). Если `PG_PWD` пуст —
   помочь пользователю проверить `grep PG_PWD /Users/ilkoid/dev/poncho-ai/.env`.
2. **Проверка свежести** — `MAX(create_date)` из `supplies WHERE status_id=5`.
   Если `lag_days > 3` — предупредить, предложить запустить downloader.
3. **Запуск скрипта** — основной `python3 scripts/supply_time.py` (или с
   флагами по запросу пользователя).
4. **Интерпретация** — посмотреть на mean / median / P90; обратить внимание
   на склады с P90 ≥ 7 дней (`⚠️` в выводе).
5. **Drill-down при аномалиях** — `--drill-down NAME` покажет отдельные
   поставки; искать выбросы (одиночная поставка, зависшая на 30 дней).
6. **Cross-check при сомнениях** — `--validate-stocks` сверит с эмпирическим
   появлением товаров в стоках; сравнить `Средний stock_lag` с `Среднее, дн`.
7. **Вывод** — markdown-таблица + 2–4 строки наблюдений (быстрый/медленный
   склад, выбросы, предупреждения о свежести).

## Границы

- **Только SELECT.** Никаких writes в БД. Все SQL — read-only.
- **Только PostgreSQL** (как требовалось в задаче). SQLite-пути отсутствуют.
- **Не вызывает WB API.** Данные уже в PG через `download-wb-supplies-v2`.
- **Primary = `updated_date` при `status_id=5`** — обоснование в
  `references/methodology.md`. Альтернатива (первая дата `stocks.quantity>0`)
  — только опциональный cross-check, потому что 25.7% поставок не сматчатся
  из-за рассинхрона имён складов.
- **Не анализирует причины задержек** — это отдельная задача (тип поставки,
  сезон, объём). Можно расширить через `--group-by` в будущих версиях.
- **Гранулярность — день.** Часовые лаги не измеряются (нет почасовых данных).
- **Замороженные склады WB.** Когда WB замораживает склад (заказы/остатки
  заморожены, поставки зависают в `status_id ≤ 4`), фильтр
  `status_id=5 AND ready_for_sale>0` автоматически отсекает такие зависшие
  поставки — они не попадут в отчёт. Это корректно (товар не стал доступен),
  но означает, что по замороженному складу в отчёт попадут только поставки,
  завершённые **до** даты заморозки. Список замороженных складов нужно
  поддерживать вручную (WB не отдаёт статус через API supplies).
  Текущий список (на 2026-07-20): **Электросталь** (заморожен с 2026-07-18).
  Детали и SQL для просмотра зависших поставок — в
  `references/methodology.md` §7.2.

## Python в `scripts/` — почему не SQL-first

В существующем навыке `sales-trend-report` весь SQL встроен в markdown и
выполняется через `psql -f /tmp/q.sql`. Здесь же — готовые `.py` скрипты в
`scripts/`. Причины:

1. **Повторяемость статистик.** Перцентили P25/P75/P90, вычисляемые через
   numpy с linear interpolation, должны давать идентичный результат на любых
   входах. В чистом SQL потребовался бы `PERCENTILE_CONT` (работает, но
   длинный и хрупкий SQL — см. `references/sql-queries.md` §4).
2. **Тестируемость.** `.py` файлы можно покрывать unit-тестами; markdown
   с встроенным SQL — нет.
3. **Cross-check логика.** `--validate-stocks` требует чтения YAML-словаря,
   итерации по поставкам, нескольких параметризованных SQL — это плохо
   укладывается в один `psql -f`.

Эталонные SQL для ручной проверки остаются в `references/sql-queries.md` —
ими можно пользоваться без Python.
