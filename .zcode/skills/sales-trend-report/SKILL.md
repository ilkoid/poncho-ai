# Sales Trend Report

Анализ трендов продаж WB по артикулам и предметам из PostgreSQL. Источник — таблица `public.sales` (RAW-слой, WB Statistics API). Считает 4 скользящих окна (4 нед / 2 нед / 1 нед / 3 дня) и классифицирует тренд через линейную регрессию прямо в SQL — без Go-кода и компиляции. Формат — read-only SELECT через `psql`.

## Когда запускать

Запускай этот skill, когда пользователь спрашивает про:
- **Тренд продаж по артикулу/SKU**: «какая динамика у артикула X», «упали ли продажи у ...», «сколько продалось за последние 28/14/7/3 дня».
- **Что растёт / падает**: «покажи топ растущих артикулов», «что деградирует», «какие SKU падают сильнее всего».
- **Агрегированный тренд по предметам/категориям**: «форма продаж по категории X», «какой предмет падает», «агрегированный тренд по категории».
- **Тренды по 1C-коллекции/сезону**: «школьный ассортимент», «коллекция Школа», «весенние/зимние товары», «продажи по сезону 1C». Фильтр через `onec_goods.season` (`'Школа'` / `'Весна'` / `'Осень'` / `'Зима'` / `'Лето'`) — см. Шаблоны 5–7. Это **единственный** случай, когда разрешён JOIN с `onec_goods` (см. раздел «Границы»).
- **Метрики и термины**: `retail_amount`, `quantity`, `subject_name`, `nm_id`, `supplier_article`, `regr_slope`, `moving window`, `velocity`, `sales trend`, `SKU trend`, `onec_goods.season`.

**Канонический источник env — `/Users/ilkoid/dev/poncho-ai/.env`** (root репозитория). Там `export PG_PWD=...` (и другие переменные: WB-ключи, `KEEPER_PWD`, …). Файл уже существует и заполнен — НЕ требуй от пользователя ручного `export`, а грузи его сам.

**Запуск psql через `.env`** (без ручного export, пароль не светится в `ps`):
```bash
zsh -c '
  set -a; source /Users/ilkoid/dev/poncho-ai/.env 2>/dev/null; set +a
  PGPASSWORD="$PG_PWD" psql -h "${PGHOST:-192.168.10.7}" -p "${PGPORT:-15432}" \
    -U "${PGUSER:-postgres}" -d "${PGDATABASE:-wb_data_prod}" \
    -A -F"|" --pset=footer=off -f /tmp/q.sql

```
- `set -a` — экспортирует все переменные из `.env` в окружение.
- `source ... .env` — файл в формате `export VAR=...` (zsh/bash-совместимый).
- `PGPASSWORD="$PG_PWD"` — pg-клиент читает пароль отсюда, а не из `ps`.
- `${PGHOST:-192.168.10.7}` — фолбэк на дефолт, если в `.env` нет хоста.

**⚠ Важно про zsh non-interactive:** `~/.zshrc` НЕ исполняется в `zsh -c` (non-interactive) — там `PG_PWD` пуст, даже если в интерактивной сессии он есть. Поэтому всегда `source .env` явно. Если встретишь `PG_PWD not found` — это значит, что `.env` забыли `source`-нуть.

**Длинный SQL — через `-f`:** если SQL многострочный (как Шаблоны 1–7), клади его во временный файл `/tmp/q.sql` и вызывай `psql -f`, а не `-c "..."`. Это обходит тройное экранирование кавычек (zsh + psql + SQL), которое особенно ломается на `$$`-долларах и кириллических литералах типа `'Продажа'`. Пример:
```bash
cat > /tmp/q.sql <<'SQL'
SELECT ... WHERE season='Школа';   -- одинарные кавычки безопасны внутри heredoc с 'SQL'
SQL
# затем psql -f /tmp/q.sql из блока выше
```

Для машиночитаемого вывода (когда результат нужно парсить) добавь `-A -F'|' --pset=footer=off`. Для человеко-читаемого (дефолт `psql`) — без этих флагов, `psql` сам нарисует таблицу.

**Если `.env` отсутствует или `PG_PWD` пуст после `source`:** скажи пользователю, что нужно выставить переменную в `/Users/ilkoid/dev/poncho-ai/.env` (формат: `export PG_PWD=...`), и приведи пример. Не пытайся подключиться с пустым паролем — будет `fe_sendauth: no password supplied`.

## Что считается

- **Метрики** (две, параллельно): `SUM(quantity)` — штуки, `SUM(retail_amount)` — выручка в рублях.
- **Окна**: 28 дней (4 нед), 14 (2 нед), 7 (1 нед), 3 дня. Анкорятся **от последней доступной даты в БД** (`MAX(sale_dt::date)`), а не от `CURRENT_DATE`. Реализовано через `SUM(...) FILTER (WHERE d >= last_d - N)` в одном проходе.
- **Фильтр строк**: только продажи без возвратов — `doc_type_name = 'Продажа' AND is_cancel = false`. Возвраты (`doc_type_name = 'Возврат'`) и отмены (`is_cancel = true`) исключены.
- **Группировка**: по артикулу (`supplier_article` + `nm_id`) или по предмету (`subject_name`) для агрегированного отчёта.

## Свежесть данных (важно)

Загрузка `sales` идёт через `run-daily-analytics.sh`, и последние дни могут быть не догружены. Поэтому **первым шагом всегда** выполняй алерт-запрос:

```sql
SELECT MAX(sale_dt::date) AS last_data_date,
       CURRENT_DATE - MAX(sale_dt::date) AS lag_days
FROM sales
WHERE doc_type_name='Продажа' AND is_cancel=false;
```

Если `lag_days > 3` — выведи в шапке отчёта предупреждение:
> ⚠ Данные в БД по `{last_data_date}`, отставание `{lag_days}` дн. Окна рассчитаны от этой даты. Чтобы обновить данные, запусти `bash run-daily-analytics.sh`.

Окна анкорятся от `last_data_date` именно затем, чтобы тренды не искажались отсутствием свежих дней (иначе `w7_qty` / `w3_qty` обнулятся для всех артикулов и всё будет выглядеть как «стабильное падение»).

## Классификация тренда (линейная регрессия)

Тренд определяется **в самом SQL** через встроенные агрегаты PostgreSQL:
- `regr_slope(Y, X)` — наклон линейной регрессии Y по X. Знак = направление, величина = скорость изменения в единицах метрики в день.
- `regr_r2(Y, X)` — коэффициент детерминации R² (0..1). Высокий = точки близко к прямой = тренд «чистый», низкий = шумно/волатильно.

Здесь Y = дневная метрика (qty или rev), X = номер дня (0 = 28 дней назад, 27 = сегодня).

**6 меток тренда** (полные правила и CASE-выражение — в `references/trend-rules.md`):
| Метка | Символ | Что значит |
|---|---|---|
| `stable_up` | ↑ | Растёт устойчиво (R² ≥ 0.4, наклон ≥ +2%/день) |
| `stable_down` | ↓ | Падает устойчиво (R² ≥ 0.4, наклон ≤ −2%/день) |
| `volatile_up` | ↗ | Растёт, но шумно (R² < 0.4) |
| `volatile_down` | ↘ | Падает, но шумно (R² < 0.4) |
| `neutral` | → | Наклон < 2%/день в любую сторону |
| `no_data` | · | Нет продаж за 28 дней |

Метки считаются параллельно для qty и rev. Если они расходятся (например, qty растёт, rev падает) — это важный сигнал о деградации цены/скидки, обязательно отметь это в выводе.

Подробные пороги, готовое CASE-выражение и интерпретация R² → читай `references/trend-rules.md`.

## Формат вывода

Выведи markdown-таблицу. Для отчёта по артикулам:

```markdown
## Тренд продаж по артикулам — за последние 28 дней

DSN: `wb_data_prod@192.168.10.7:15432` · фильтр: `subject_name = 'Панама'` · окно: 28 дней

| Артикул | Предмет | 28d шт | 14d шт | 7d шт | 3d шт | Тренд qty | R² | 28d выручка | Тренд rev |
|---|---|---:|---:|---:|---:|:---:|---:|---:|:---:|
| 12345678 | Панама | 280 | 154 | 91 | 42 | ↑ stable_up | 0.82 | 145 600 ₽ | ↑ stable_up |
| 87654321 | Панама | 410 | 180 | 70 | 24 | ↘ volatile_down | 0.31 | 198 300 ₽ | ↘ volatile_down |

**Краткий вывод (2–4 строки):**
- 1 артикул устойчиво растёт (↑ stable_up), 1 — падает (↘ volatile_down).
- У артикула 87654321 qty и rev падают согласованно → реальная просадка, не скидка.
- ...
```

Для агрегированного по предметам — та же структура, но строки = `subject_name`, без колонок конкретного артикула.

Если данные по `retail_amount` расходятся с `quantity` (один растёт, другой падает) — обязательно отметь это в кратком выводе.

   - «какие предметы растут/падают в коллекции» → запрос #7 (агрегация внутри коллекции).
   - «детально по артикулам коллекции» → запрос #5 (если нужен полный список).
   - Если упомянута коллекция/сезон 1C — подставь `'Школа'`/`'Весна'`/... в фильтр `season`. **Никогда `ILIKE '%школьн%'`** — только точное совпадение `season = 'Школа'`.
4. **Подставь фильтры** — конкретные значения `subject_name`/`supplier_article`/`brand_name`/`LIMIT` из вопроса пользователя.

6. **Проинтерпретируй** — для каждой строки определи метку тренда по `trend_qty`/`trend_rev` (CASE уже в SQL), объясни R² если он низкий, отметь расхождения qty↔rev.

## Границы

- **Только SELECT.** Никаких write-операций в БД, никаких мутаций WB API.
- **Главный источник** — `public.sales` (всё нужное уже там: `subject_name`, `brand_name`, `supplier_article`). JOIN с `cards` **не нужен** и запрещён — он только замедляет запрос.
- **Scoped-исключение: `onec_goods`.** JOIN с `public.onec_goods` разрешён **только** для фильтрации по 1C-коллекции/сезону, когда пользователь спрашивает про «Школу», «Весну» и т.п. Условия: (1) только read-only; (2) только по `sales.supplier_article = onec_goods.article`; (3) только поле `season` (или `collection_season` как резерв). Каноническое значение школьного сезона — `'Школа'` (с заглавной, см. AGENTS.md → «Поле season в onec_goods» и `cmd/data-analyzers/collection-readiness/config.yaml`). **Никогда не используй `ILIKE '%школьн%'`** — в данных хранится bare noun `'Школа'`, ILIKE даёт 0 матчей. Шаблоны 5–7 в `references/sql-templates.md`.
- **Пороги тренда** (rel_slope 2%/день, R² 0.4) — дефолты. Если ассортимент пользователя очень малобъёмный или наоборот массовый, пользователь может править их в `references/trend-rules.md`.
