# Правила классификации тренда

Тренд считается **в самом SQL** через встроенные агрегаты PostgreSQL `regr_slope(Y, X)` и `regr_r2(Y, X)`. Здесь — полная спецификация правил и порогов, плюс их обоснование.

> **Сноска про 1C-коллекции (Шаблоны 5–7).** При фильтрации по `onec_goods.season` (например, коллекция `'Школа'` ≈ 2880 артикулов) порог `w28_qty >= 10` из Шаблона 2/6 особенно важен: ассортимент 1C содержит много SKU с редкими продажами (раз в несколько дней), и без этого порога топ растущих/падающих оказывается забит артикулами с `slope_qty IS NULL` или единственным днём данных. Не снижай порог для коллекций без явного запроса пользователя.

## Математика

`regr_slope(Y, X)` и `regr_r2(Y, X)` — встроенные в PostgreSQL функции агрегатной линейной регрессии (метод наименьших квадратов). Не требуют расширений.

- **Y** (зависимая переменная) = дневная метрика. В наших запросах это `qty` или `rev` из CTE `daily`.
- **X** (независимая переменная) = номер дня, вычисляемый как `(d - (last_d - 27))::float8`, где `last_d = MAX(sale_dt::date)` — последняя доступная дата в БД (см. CTE `params` в `sql-templates.md`). 28 дней назад от `last_d` = 0, `last_d` = 27. Окна анкорятся от `last_d`, а не от `CURRENT_DATE`, чтобы тренд не искажался отсутствием свежих дней (см. SKILL.md → «Свежесть данных»).

Важно: `regr_slope(Y, X)` — **Y первый**, X второй. Перепутать аргументы местами — главная ошибка, даст наклон с обратной размерностью.

Возвращают:
- `slope` — наклон прямой в единицах метрики в день. Знак = направление, величина = скорость. Например, slope_qty = +3.2 = «в среднем +3.2 штуки в день за 28 дней».
- `r2` — коэффициент детерминации R², число от 0 до 1 (NULL если данных < 2 точек). 1 = точки идеально на прямой, 0 = точки случайные, 0.5 = половина дисперсии объясняется трендом.

**Нюанс про нулевые дни:** дни, когда у артикула не было продаж, не попадают в `daily` (нет строки в `sales` с `quantity > 0`). Поэтому регрессия строится только по дням с продажами. Для редкопродаваемых SKU это значит «сколько продалось в дни, когда вообще продавалось» — что для оценки тренда спроса обычно и нужно. Но если артикул продаётся раз в неделю — `r2` будет низким не из-за шума, а из-за малого числа точек; учитывай это в интерпретации.

## Относительный наклон

Абсолютный `slope` мало что говорит: +5 шт/день — это много для артикула со средними продажами 2 шт/день, и пренебрежимо мало для артикула с 1000 шт/день. Поэтому нормируем:

```sql
rel_slope = slope_qty / NULLIF(w28_qty / 28.0, 0)
```

`w28_qty / 28.0` — средние дневные продажи за 28 дней. `rel_slope` — наклон как доля от среднего. Например, `slope_qty = 0.5`, среднее = 10 → `rel_slope = 0.05` = +5%/день.

`NULLIF(..., 0)` защищает от деления на ноль для свежих артикулов (где `w28_qty = 0`).

## Пороги (дефолты)

| Метка | Условие | Что значит |
|---|---|---|
| `no_data` | `w28_qty IS NULL OR w28_qty = 0` | Нет продаж за 28 дней. Тренд не определён. |
| `neutral` | `|rel_slope| < 0.02` | Наклон < 2%/день. Артикул «стоит на месте» в среднем, даже если день-к-дню скачет. |
| `stable_up` | `rel_slope >= 0.02 AND r2_qty >= 0.4` | Растёт на ≥ 2%/день, и точки ложатся на прямую (R² ≥ 0.4). Это «настоящий» тренд. |
| `stable_down` | `rel_slope <= -0.02 AND r2_qty >= 0.4` | Падает на ≥ 2%/день, точки на прямой. Реальная просадка. |
| `volatile_up` | `rel_slope >= 0.02 AND r2_qty < 0.4` | В среднем растёт, но шумно/скачкообразно. Тренд есть, но доверия меньше. |
| `volatile_down` | `rel_slope <= -0.02 AND r2_qty < 0.4` | В среднем падает, но шумно. |

**Почему `0.02` (2%/день):** за 28 дней накопленный эффект 2%/день ≈ +56% или −46% — граница между «статистическим шумом» и «заметным движением». Меньше 2%/день — обычно невооружённым глазом не видно.

**Почему R² `0.4`:** это граница «умеренной» корреляции в статистике (0.4–0.7). Ниже 0.4 — больше половины дисперсии не объясняется трендом, то есть значительную часть движения составляет шум.

Эти пороги — **разумные дефолты для массового ассортимента WB**. Если у пользователя специфический ассортимент (например, дорогие редкие товары или масс-маркет с большим оборотом), можно скорректировать:
- Масс-маркет (высокий оборот, много точек в регрессии): можно поднять R² до 0.5–0.6, опустить rel_slope до 0.01.
- Низкооборотные премиум-SKU: опустить R² до 0.3, поднять rel_slope до 0.03–0.05.

Скорректируй пороги прямо в CASE-выражениях в SQL-запросах, если видишь, что распределение меток по реальным данным выглядит неразумно (например, 90% `volatile_*` или почти нет `stable_*`).

## Готовое CASE-выражение

Для `trend_qty` (для `trend_rev` аналогично — замени `qty` на `rev` и `w28_qty` на `w28_rev`):

```sql
CASE
    WHEN w28_qty IS NULL OR w28_qty = 0 THEN 'no_data'
    WHEN ABS(slope_qty / NULLIF(w28_qty / 28.0, 0)) < 0.02 THEN 'neutral'
    WHEN slope_qty > 0 AND r2_qty >= 0.4 THEN 'stable_up'
    WHEN slope_qty < 0 AND r2_qty >= 0.4 THEN 'stable_down'
    WHEN slope_qty > 0 AND r2_qty < 0.4  THEN 'volatile_up'
    WHEN slope_qty < 0 AND r2_qty < 0.4  THEN 'volatile_down'
    ELSE 'neutral'
END AS trend_qty
```

`ELSE 'neutral'` ловит edge-case: `slope_qty = 0` ровно (бывает при плоских продажах, R² = 0).

## Интерпретация R²

| R² | Что значит | Как описывать пользователю |
|---|---|---|
| ≥ 0.7 | Сильный, точки близко к прямой | «устойчивый тренд, точки ложатся на прямую» |
| 0.4 – 0.7 | Умеренный, направление видно, но есть разброс | «тренд есть, но с разбросом по дням» |
| < 0.4 | Слабый, направление угадывается, но точек мало или они шумные | «волатильно, направление в среднем такое, но день-к-дню сильно скачет» |
| NULL | Меньше 2 точек данных | «недостаточно данных для регрессии» |

## Расхождения qty ↔ rev

Метки считаются параллельно для `trend_qty` и `trend_rev`. Если они расходятся — это **важный диагностический сигнал**, обязательно отметь в выводе:

| trend_qty | trend_rev | Что значит |
|---|---|---|
| up | up | Здоровый рост — продаётся больше, выручка тоже растёт. |
| down | down | Здоровая просадка — и штуки, и деньги падают согласованно. |
| **up** | **down** | **Деградация цены/скидки** — продаётся больше, но выручка падает. Возможные причины: глубокая скидка, рост доли дешёвых размеров, обвал розничной цены. **Точно подсвети это пользователю.** |
| **down** | **up** | **Улучшение юнит-экономики** — продаётся меньше, но выручка растёт. Например, рост цены при удержании части спроса. |
| neutral | up/down | Выручка двигается при плоском объёме = изменение цены, а не спроса. |

## Как презентовать результат

1. **Таблица** с колонками article/subject, окнами (`w28_qty`/`w14_qty`/`w7_qty`/`w3_qty`), `w28_rev`, метками `trend_qty`/`trend_rev`, и R² (если низкий — пользователь сразу видит, что тренд «волатильный»).
2. **Краткий вывод** (2–4 строки): сколько артикулов в каждой категории тренда, главные «истории» (например, «артикул 12345 упал на 60% за неделю — стоит проверить наличие и остатки»), расхождения qty↔rev.
3. **Символы** ↑ ↓ ↗ ↘ → помогают глазу быстрее ориентироваться в таблице, но текстовое название метки (`stable_up`, `volatile_down`) — тоже обязательно, для однозначности.

## Что НЕ делает классификация

- **Не предсказывает будущее.** Тренд описывает последние 28 дней, а не следующую неделю. «Stable_up» не значит «будет расти и дальше» — возможно, рост уже насыщается.
- **Не учитывает сезонность.** Линейная регрессия не моделирует недельные/месячные циклы. Если артикул явно «выходного дня», регрессия покажет низкий R² → `volatile`, что технически корректно (шумно), но не объясняет природу. Для таких случаев используй **запрос #4 (drill-down)** — он покажет дневную форму.
- **Не различает причину.** Падение из-за out-of-stock и падение из-за потери спроса в тренд-анализе выглядят одинаково. Если тренд `stable_down` — это повод копать глубже (остатки, позиции в поиске, конкуренты), но не вердикт сам по себе.
