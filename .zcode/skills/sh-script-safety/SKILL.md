# Протокол правки sh-скриптов конвейера

**Почему это критично (слова пользователя, 31.10):** правки скриптов запуска — «крайне важная и чувствительная область, влияет на непрерывность бизнеса». Прогоны идут ночью без человека.

**Как скрипт доезжает до машин — первое, что выяснить до правки:**
- **Mac** — крон запускает скрипты из рабочего дерева (`go run`): правка+коммит = живая немедленно.
- **VPS2** — ночной non-fatal `git pull` в 00:05 (download-all-v2.sh): коммит уезжает сам, ff-only; локальные правки VPS2 должны переживать каждый pull.

Ошибка, закоммиченная вечером, сама едет в ночь. Поэтому проверки ниже — не церемония, а единственный барьер.

## Шаг 0. До правки — разведка

1. Прочитай точную зону правки Read-инструментом (соседние строки, не весь файл вслепую).
2. Конвенции конкретного скрипта: `log` vs `echo` (VPS2-скрипты логируют через `log`), переменные `$PONCHO`/`$C`, однострочные вызовы `run go run ...` как у соседей, стиль комментариев.
3. Функции-обёртки (`run`, `maint`, `log`) определены ВЫШЕ точки вставки; узнай их семантику (`run` считает RUN_COUNT, берёт basename $3 для Summary).
4. Счётчики Summary: динамические (RUN_COUNT) или хардкод? Вырастут сами или надо править цифру?
5. Снимиок «до»: счётчики `run go run` / `maint` / фаз-маркеров — ожидаемая арифметика известна ЗАРАНЕЕ.

## Шаг 1. Правка

- Минимальный дифф: точная замена Edit-инструментом, не sed-вслепую.
- Комментарий отвечает «почему», а не «что», со ссылками file:line (сваггер, логи, инцидент-дата).
- Если добавляешь вызов утилиты — реши вопрос периодов/флагов для ИДЕНТИЧНОСТИ с другими фазами (пример: funnel-csv без `--days`, чтобы период совпадал с промо-фазой для resume).

## Шаг 2. Синтаксис — три парсера

```
bash -n <script>       # первичный: крон зовёт /bin/bash
zsh -n <script>        # второй парсер, ловит другой класс ошибок
/bin/sh -n <script>    # диагностический
```

- `bash -n` и `zsh -n` обязаны быть чистыми.
- `/bin/sh -n` может упасть на СТАРОМ башизме (пример: `exec > >(tee ...)` в download-all-v2.sh:47). Это НЕ твой регресс, если: (а) `git show HEAD:<file> | /bin/sh -n` падает так же; (б) `crontab -l` на обеих машинах зовёт `/bin/bash`. Чужие башизмы не чинить в своём коммите.

## Шаг 3. shellcheck

`shellcheck -S error <script>` — 0 ошибок обязательно (0.11.0 стоит на Mac). Если shellcheck нет — углублённые структурные гаранты, не ставить без спроса.

## Шаг 4. Структурные гаранты

- `grep -c "<уникальный маркер>"` — ровно ожидаемое число вхождений (например: добавил одну фазу — вызов утилиты встречается 1 раз в этом скрипте).
- Порядок фаз: `grep -n "Phase"` — новая фаза на месте (до/после нужных).
- Существование: конфиг по `$C/...` существует, `go build` утилиты зелёный.
- Пересчёт счётчиков из шага 0 = снимок ± ожидаемое; нет осиротевших ссылок на удалённое; целостность `${DAYS}`.

## Шаг 5. Пред-полёт машин

- **VPS2** (через `~/bin/vps2`, read-only): `git log --oneline -1` — HEAD предок нового коммита; `git status --short -- <файл>` — целевой скрипт НЕ локально модифицирован там (иначе ff-pull молча не применится — скрипт продолжит старую версию).
- Mac: скрипт в рабочем дереве уже содержит правку (она и есть источник коммита).
- Крон-обёртки (run-*-daily.sh) не задеты, если не были целью.

## Шаг 6. Стейджинг и дифф

- Коммитить файлы ЯВНО поимённо (не `-a`): в рабочем дереве живут чужие эксперименты параллельных сессий.
- Если в файле есть чужой незакоммиченный ханк — стейджить ТОЛЬКО свой: `git diff <file>` → выделить свой hunk → `git apply --cached <patch>`; затем grep staged-диффа на чужие маркеры (пример 31.10: PGHOST-ханк остался в дереве, в коммит не попал).
- Полный `git diff` показать пользователю. Коммит+пуш — ТОЛЬКО после явного «ок».

## Шаг 7. После коммита и до ночи

- `git show HEAD:<file> | bash -n` — синтаксис ЗАКОММИЧЕННОГО блоба (то, что реально уедет).
- Сформулируй критерии утренней сверки ДО ночи (какая строка в логе, какой счёт в Summary, на какой машине) — и запиши в туду.
- VPS2 разворачивается СВОИМ ночным pull, не ручным (если пользователь явно не попросил ручной).

## Гатчи из инцидентов (не повторять)

- **PATH-моки и враперы (17.10):** run-download-all-daily.sh препендит homebrew PATH — настоящий `go` обгоняет мок, «тест» запускает РЕАЛЬНЫЕ утилиты (случайный живой прогон). Мок-тестировать только внутренние скрипты напрямую; враперы — диффом к эталону.
- **Lock-артефакты:** убитый прогон оставляет lock ФАЙЛОМ (0 байт) — `mkdir` падает всегда, `find -type d` не матчит. После тестов/убийств: `ls .download-all*.lock` и вычищать.
- **Протухший lock:** промо-лок >4ч удаляется скриптом сам, но только если он каталог — см. предыдущий пункт.
- **`/bin/sh` на darwin ломает `echo -n`** — в psql-вставках использовать printf.
