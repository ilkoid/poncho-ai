# Semantic Audit — аудит планов по бизнес-логике

Проверка того, что план оперирует **правильными доменными сущностями**, а не
похожими словами. Типовые ловушки: «продажи» посчитаны по заказам; возврат
обработан как отмена заказа; остаток спроектирован как поток, хотя источник —
снапшот; нетто и валовая выручка смешаны в одном показателе.

Два режима:

- **Вердикт роли analyst** (журнал kb): вопрос пришёл через `kb_threads`,
  ответ — `kind=verdict` с `reply_to` и evidence.
- **Self-check рабочего агента**: тот же чек-лист до публикации плана;
  выявленные сомнения — в вопрос аналитику, а не молча в код.

## Протокол заземления (обязателен)

Диалог — для уточнений, не для фактов. Ни одно утверждение о данных, спеке или
коде не выдаётся без проверки по источнику:

| Утверждение о... | Источник | Evidence в kb |
|---|---|---|
| данных | MCP `pg-readonly-test` (wb_data_test), при необходимости `pg-readonly` (prod, READ ONLY) | `db` + `as_of` |
| спеке WB | `docs/wb_api_swagger/12-reports.yaml` (канон orders/sales), др. YAML | file:line в тексте |
| коде/схеме | чтение `pkg/storage/postgres/*_schema.go`, `pkg/*/types.go` | `git` sha |
| семантике денег | `dev_region_sales_replacement.md` (две семантики), CLAUDE.md «Sales Data Pipeline» | ссылка в тексте |

Правила: только агрегирующие SELECT (без дампов фактов); не проверено —
помечай «не проверено», не выдумывай; короткие слова trgm не ищет.

## Словарь доменов (карта; источник истины — живая схема)

Возвраты **не имеют своей таблицы** — это строки в чужих:

| Домен | Где живёт | Ключ/маркер | Семантика |
|---|---|---|---|
| Заказ | `orders` | PK `srid` | оформленный заказ WB; `order_date` ≠ дата продажи |
| Заказ FBS | `fbs_orders`, `fbs_orders_status(_log)`, `fbs_supplies` | srid + статусная лента | отдельный контур со своими статусами |
| Лента заказов | `order_feed` | — | `seller_price` — **валовая** цена |
| Продажи (3 среза) | `orders` → `operational_sales` → `sales` | см. ниже | early signal → операционные → финансовая реализация; **это разные ответы, не стадии одной таблицы** |
| Операционные продажи | `operational_sales` | `sale_id`: `S*` продажа, `R*` возврат | `for_pay` — **нетто** (продажи − возвраты) |
| Финансовые продажи | `sales` | `rrd_id`; `doc_type_name` «Продажа»/«Возврат» | realization; даты `order_dt`/`sale_dt`/`rr_dt` |
| Региональные продажи | `region_sales`, `service_records` | — | аналитический срез по регионам |
| Остатки | `stocks_daily_warehouses`, `stock_history_*` | дата+склад | **снапшот на дату**, не поток |
| Остатки 1С | `onec_rests` | — | второй источник остатков; сверка с WB — отдельная задача |
| Движения склада | `warehouse_remains` | `row_kind`, вкл. `in_transit_return` | «в пути возвраты на склад WB» — возврат как движение остатка |

## Чек-лист аудита плана

Каждому пункту — статус: ✅ соответствие / ❌ несоответствие (severity) /
⚠️ сомнение / N/A. Все ❌ и ⚠️ — с evidence.

| # | Проверка | Severity |
|---|---|---|
| SA-1 | Срез продаж выбран по назначению показателя: тренд «что продаётся» — `operational_sales`; деньги/финансы — `sales`; ранний сигнал — `orders`. Срез назван в плане явно | CRITICAL |
| SA-2 | Возвраты: план различает возврат и отмену; знак/фильтр `R*` и «Возврат» указан; выбрано нетто (`for_pay`) или брутто осознанно; возврат как движение остатка (`in_transit_return`) учтён там, где про остатки | CRITICAL |
| SA-3 | Заказ ≠ продажа: конверсия/отмены/доставка не потеряны; `order_date` не используется как дата продажи | CRITICAL |
| SA-4 | Остатки: снапшот или поток — план не смешивает; `stocks_daily_warehouses` — срез на дату; удвоение при джойне снапшотов исключено | WARNING |
| SA-5 | Гранулярность: PK источника (`srid`/`sale_id`/`rrd_id`) известна плану; агрегаты не порождают дубли (UNIQUE покрывает варьируемые поля); int8/numeric для ID и денег | CRITICAL |
| SA-6 | Даты: названа рабочая дата показателя (`order_dt` vs `sale_dt` vs `rr_dt` vs `last_change_date`); таймзона МСК; граница «вчера без сегодня» | WARNING |
| SA-7 | Деньги: валюта семантики ясна (валовая `seller_price` vs нетто `for_pay`, комиссии/НДС); показатели не смешивают | CRITICAL |
| SA-8 | FBS/DBS-контур: если план про заказы — FBS-статусы и supplies не забыты | WARNING |
| SA-9 | Источник каждого числа: показатель → таблица+поле (+сверка со схемой `*_schema.go`); «примерно» нет | CRITICAL |
| SA-10 | Требования измеримы: результат плана проверяем запросом к данным (написан хотя бы набросок проверочного запроса) | WARNING |

## Выход (вердикт)

`kb_ask` в тот же тред: `kind=verdict`, `reply_to` = id вопроса.

Структура тела: соответствие/несоответствие в целом → таблица SA-1..SA-10 →
разбор каждого ❌/⚠️ с evidence и предложенной правкой плана → что проверить
живым прогоном. Объём — по делу (читателю хватит ~12 КиБ).

Дальше решает автор вопроса: правит план и закрывает тред `resolution` либо
уточняет вопросом. Вердикт план не правит и код не пишет.
